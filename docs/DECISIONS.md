Фиксация решений транспорта MAX для CryptoLayer. Источники фактов:
`.omo/drafts/max-transport-module.md` (findings, решения владельца D1–D7),
`docs/vkmax-contract.md` (спайк задачи 2 — источник истины по vkmax),

## ADR-1: выбор библиотеки — vkmax

**Статус:** принято (владелец подтверждён молчанием при брифинге; спайк задачи 2
зафиксировал контракт). **Дата:** 23.08.2026.

Официального пользовательского API у MAX нет. Боты исключены (ADR-2), значит
транспорт строится на неофициальном user-API. Проверено ~11 кандидатов;
сравнение по критериям плана (активность проекта, доступность установки,
вход по токену из web.max.ru, документация протокола):

| pyromax | ❌ alpha | — | — | — | нет |

Остальные кандидаты из обзора экосистемы (форки/обёртки вокруг Bot API и SDK
официального ботовского направления: maxapi, aiomax, maxapi-sdk, maxbot-sdk)
отпадают целиком: они построены поверх Bot API, использование которого
исключено решением владельца (ADR-2).

Дополнительные факторы в пользу vkmax:

- async (aiohttp/websockets) — мостится в синхронный мир ядра штатно (ADR-4);
- отправка `send_message(client, chat_id, text)` → opcode 64 совпадает с
  задокументированным v11; приём через callback с push-пакетами op=128;
- полный набор функций (edit/delete/pin/reply/upload) оставляет запас на будущее,
  хотя v1 использует только текст.

**Уточнение спайка (задача 2):** ставится не PyPI-wheel 1.0.2, а git-коммит
`c67a5097ac3e565dfb5d2448f9b17aff7f92a596` — wheel расходится с документированным
API репозитория (нет `device_id` в `login_by_token`, нет Origin-заголовка,
recv-loop не переживает обрыв). Подробности и RISK-блок: `docs/vkmax-contract.md` §11.
Каноничная строка в `Max/requirements.txt`:

```
vkmax @ git+https://github.com/nsdkinx/vkmax@c67a5097ac3e565dfb5d2448f9b17aff7f92a596
```

**Критерии реверса зависимости** (если vkmax перестаёт работать — дрейф
приватного протокола, смерть проекта): по порядку

1. Форки vkmax / переход на ближайший живой клон того же протокола (WebMax —
   запасной TOP-2 из той же ниши WebSocket web.max.ru).
2. Вендоринг исходников vkmax в наш репозиторий и точечные правки адаптера
   (адаптер тонкий: все точки касания перечислены в contract.md §13).
3. Собственный клиент по opcodes: протокол v11 задокументирован в самом vkmax
   (`docs/opcodes.md`), критические методы — login=19, send=64, приём push=128,
   disconnect; реализация двух эндпоинтов на stdlib+websockets посильна.

**SMS-логин отложен:** token-флоу (`login_by_token`) достаточен для v1;
SMS-флоу (`send_code`/`sign_in`) в vkmax есть, но не используется.

## ADR-2: отказ от ботов и Bot API; позиция по ToS

**Статус:** принято (решение владельца). **Дата:** 23.08.2026.

Решение владельца, цитата из брифинга: **«боты мы никак не используем. Вообще.
Используем все кроме ботов»**. Мотивация: создание бота MAX требует статуса
юрлица/ИП/самозанятого резидента РФ с верификацией (Госуслуги/банк) через
платформу «MAX для партнёров» — статус есть не у всех сторон обмена, а схема
«общий бот» технически рискованна (семантика marker при параллельных читателях
`GET /updates` не задокументирована).

Следствия: никаких обращений к `platform-api*.max.ru`, @MasterBot, webhook/subscriptions;
только user-API (ADR-1). Дополнительный технический аргумент против Bot API:
лимит 2 сообщения/сек на диалог и требование сертификата Минцифры в доверенных.

**Позиция по ToS.** Официального юзерского API у MAX нет, поэтому любой
пользовательский транспорт имитирует веб-клиент и нарушает условия использования
MAX. Это принятое владельцем решение с известным риском блокировки аккаунта;
README модуля обязан содержать явную ремарку об этом (требование владельца D2),
без смягчений. Использование — на свой риск.

## ADR-3: анти-флуд пейсинг отправки

**Статус:** принято (требование владельца D3). **Дата:** 23.08.2026.

Цель — чтобы сообщения уходили «как человек пишет», с промежутками, а не пачкой:
это и защита от флуд-лимитов сервера, и маскировка трафика.

Реализация (см. `Max/main.py`, Sender):

- `send(text)` всегда неблокирующий: кладёт текст в ограниченную очередь
  `queue.Queue(maxsize=1000)` через `put_nowait()`; при переполнении — warning
  и немедленный дроп (ретраи пакетов — работа ядра).
- Worker-поток берёт по одному сообщению и ждёт случайную паузу
  `random.uniform(min_pause, max_pause)` через единственный прерываемый
  примитив `stop_event.wait(...)` (никакого `time.sleep`). Дефолты пауз —
  **2–6 секунд**, настраиваются credentials («Мин./Макс. пауза, сек»),
  пустое значение = дефолт.
- Классификация ошибок отправки: транзиентные (таймауты, обрывы соединения,
  флуд/ratelimit маркеры, `None`-результат = «сервер молчит») → экспоненциальный
  backoff base 5 c, cap 120 c, ретрай пока stop_event чист; терминальные
  (auth/permission/несуществующий chat_id по строковым маркерам; ошибки без
  классифицируемого текста — после 5 неудач подряд одного сообщения) → ERROR
  с actionable-сообщением («проверьте Token / Chat ID»), очередь очищается,
  worker останавливается. Успех сбрасывает счётчик.

### Взаимодействие с ядром: пропускная способность и семантика потерь

Номинальная пропускная способность: при паузах 2–6 c средний интервал ~4 c,
то есть около **80 секунд на сообщение ~1 КБ** (~10 чанков по ~100 байт плюс
ACK-трафик ядра). Это осознанная цена незаметности; ядро CryptoLayer само режет
данные на чанки и ретраит пакеты, поэтому модулю достаточно best-effort доставки
текста.

Семантика потерь: при затяжном троттлинге или сетевых ошибках backoff растёт
до 120 c на попытку, и очередь отправки может накапливаться. Если суммарная
задержка превысит окно ядра «дроп пакетов старше 5 минут», хвостовые чанки
будут молча потеряны концом-в-конец (ядро отбросит их как просроченные ещё до
попадания в модуль, либо получатель не дождётся хвоста). Это **принятое
ограничение v1**: восстановление целостности длинных передач при затяжном
троттлинге сознательно отдано оператору (уменьшить паузы, перезапустить передачу),
а не усложнению протокола модуля.

### ADR-3a: эмуляция «печатает…» — НЕТ

Вердикт спайка (contract.md §12): **NO**. Ни одной функции или opcode статуса
набора текста в пакете vkmax нет (grep `typing|set_status` — пусто, в
`docs/opcodes.md` такого метода тоже нет). Эмуляция «печатает…» не имплементируется;
если она появится в будущих версиях протокола — вопрос переоткрытия ADR.

## ADR-4: threading-мост, callback-driven Listener, правило адресата

**Статус:** принято. **Дата:** 23.08.2026.

Ядро CryptoLayer синхронное, vkmax — асинхронная библиотека. Мост — паттерн
Telegram-модуля сборника cryptolayer-modules:

- `create_session(ingester)` создаёт выделенный daemon-поток с собственным
  циклом событий (`asyncio.new_event_loop()`, дефолтный ProactorEventLoop на
  Windows совместим — contract.md §12); все вызовы vkmax уходят туда через
  `asyncio.run_coroutine_threadsafe(...).result(timeout)`.
- Каждый вызов оборачивается таймаутом (`asyncio.wait_for`): у `invoke_method`
  внутри vkmax таймаута нет вовсе (contract.md §7), молчание сервера = вечное
  зависание. Логин — 30 c, отправка — 45 c, disconnect — 10 c.
- Listener — callback-driven: `set_packet_callback(async fn(client, packet))`
  (синхронная регистрация до ожидания входящих). Обработчик ТОЛЬКО фильтрует
  пакет и кладёт текст в FIFO-очередь; ровно один worker-поток вызывает
  `ingester`. Произвольный downstream-код ядра никогда не исполняется в потоке
  цикла событий, иначе страдает ws-heartbeat; несколько консьюмеров запрещены —
  порядок чанков ядра равен порядку доставки только при одном потребителе.
  Очередь ingest ограничена (10000): при переполнении дропается новейший чанк,
  доставленный префикс остаётся непрерывным для сборки ядра.
- Реконнект: внутреннего автопереподключения у vkmax нет (verdict NO,
  contract.md §12), поэтому поток `listen()` сам следит за живостью recv-loop:
  при обрыве новый `MaxClient()` → `connect()` → `login_by_token` с паузами
  5→10→20→40 c (cap 60 c); после 5 неудач подряд — терминальный ERROR
  («MAX connection lost permanently») и тихий выход (ядро обнаружит таймаут
  своего пинга).
- Остановка: общий `stop_event` `BaseModule` — единственный сигнал; идемпотентная
  teardown-последовательность (worker'ы → poison pill → `client.disconnect()`
  под try/except, потому что disconnect у vkmax НЕ идемпотентен → отмена
  отложенных задач → join потоков → закрытие цикла).

**Правило адресата:** адрес диалога ЕДИНСТВЕННЫЙ — credential **«Chat ID»**
(MAX-диалоги адресуются числовым chatId). Аргумент `user_id` конструкторов
валидируется на непустоту; при расхождении с Chat ID пишется warning, приоритет
у Chat ID. Фильтрация входящих требует собственного id (`my_id` из ответа логина):
echo-петля собственных сообщений исключается только сравнением
`payload.message.sender != my_id`, дегрейд-режима «только по chat_id» нет.
